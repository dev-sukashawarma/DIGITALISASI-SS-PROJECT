Analisis Query Performance Database Kamu

Berdasarkan data statistik pg_stat_statements yang kamu kirimkan, ini analisis riil ke mana performa databasemu pergi.

⚠️ Ringkasan 4 Bottleneck Terbesar

PeringkatQuery / KomponenPorsi Waktu DBStatusRekomendasi Tindakan
1 🔴 realtime.list_changes (Websocket engine) 73.48% Bypassable Audit & matikan realtime di tabel yang tidak butuh live update.
2 🔴 system_health_latest (View status) 1.20% (872ms/query) Sakit Buat index composite baru pada target_name dan checked_at.
3 🟡 daily_checklist_ticks (Checklist ticks) 8.85% (59ms/query) Degraded Optimasi RLS Policy atau gunakan service_role untuk server-side.
4 🟡 pg_timezone_names (Connection Churn) 5.07% (670ms/query) Sistem Aktifkan Supabase Connection Pooling (port 6543) di Next.js.

1. Supabase Realtime: realtime.list_changes (73.48%)

Fungsi ini memproses log replikasi (WAL) database setiap ada operasi INSERT, UPDATE, atau DELETE pada tabel yang diaktifkan realtimenya.

ℹ️ Kenapa ini memakan 73% database?

Sebab fungsi ini dipanggil 2.115.899 kali. Per query sangat cepat (8.8ms), namun karena dipanggil jutaan kali, ia menjadi konsumen CPU terbesar. Hal ini normal di Supabase jika kamu mengaktifkan publikasi realtime pada tabel dengan frekuensi update tinggi (seperti log, target, atau transaksi POS).

Rekomendasi: Audit tabel yang terdaftar di supabase_realtime publication. Jika ada tabel yang tidak pernah dibaca secara realtime di frontend, hapus dari publication.

2. Riwayat System Health: system_health_latest (872.24 ms)

Query ini sangat lambat karena menggunakan DISTINCT ON (target_name) ... ORDER BY target_name, checked_at DESC.

🚨 Penyebab Utama

Index yang kamu miliki saat ini adalah (target_type, target_name, checked_at DESC). Karena diawali oleh target_type, index ini tidak dapat digunakan untuk mengoptimalkan urutan berdasarkan target_name terlebih dahulu. Database terpaksa melakukan sequential scan seluruh tabel dan sort manual.

Solusi: Jalankan perintah ini di SQL Editor untuk membuat index yang tepat secara aman tanpa me-lock tabel:

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_system_health_log_distinct_latest
  ON system_health_log (target_name, checked_at DESC);

3. Checklist Ticks: daily_checklist_ticks (59.06 ms)

Query ini dipanggil 38.000 kali. Rata-rata 59ms untuk sekadar mengambil item_id tergolong lambat.

🔒 Overhead RLS

Setiap kali kita memanggil query ini, RLS policy memaksa PostgreSQL untuk mencocokkan outlet staff: JOIN daily_checklist_records r JOIN outlet_staff s WHERE s.id = auth.uid(). Join berulang ini menurunkan kecepatan database secara drastis saat di-query puluhan ribu kali.

Solusi: Jika pemanggilan ini murni dari server-side Next.js, pastikan Next.js terhubung menggunakan service_role client (yang mem-bypass RLS secara bawaan) daripada token user biasa jika memang aman untuk dibaca secara global oleh server.

4. Query Sistem PostgreSQL: pg_timezone_names (670.64 ms)

Query ini dipanggil 1.929 kali dengan durasi 670ms per query. Ini adalah query deteksi metadata bawaan PostgreSQL.

Mengapa Terjadi? Koneksi database baru sering dibuka-tutup oleh server Next.js di cPanel (Connection Churn). Setiap koneksi baru memicu query metadata ini.

Solusi:

  • Gunakan port **6543** (Connection Pooler Supabase) di konfigurasi database aplikasi Next.js kamu.
  • Matikan auto-detect timezone pada driver database (misal Prisma / Kysely / Drizzle) dan set timezone secara manual di connection string: ?options=-c%20timezone=Asia/Jakarta.
