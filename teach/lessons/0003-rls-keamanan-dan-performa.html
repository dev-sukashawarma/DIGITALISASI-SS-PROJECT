Row Level Security (RLS): Keamanan & Performa

Di Supabase, RLS menjaga agar data outlet tidak bocor ke outlet lain. Tapi RLS yang salah tulis bisa membuat database sangat lambat. Mari kita bahas.

🎯 Tujuan Lesson Ini

  • Memahami konsep dasar Row Level Security (RLS) di PostgreSQL
  • Memahami bahaya RLS Recursion (Rekursi RLS) dan cara menghindarinya
  • Menganalisis fungsi kunci di projectmu: accessible_outlet_ids()
  • Mengetahui cara menulis policy RLS yang cepat dan efisien

🛡️ Apa itu RLS (Row Level Security)?

Secara default, jika kamu menjalankan query SQL SELECT * FROM orders, database akan mengembalikan semua baris data. Di aplikasi multi-outlet seperti Suka Shawarma, ini bahaya: staff di Outlet Dramaga tidak boleh melihat data transaksi di Outlet Sudirman.

RLS adalah fitur di mana database otomatis menempelkan filter keamanan tambahan di setiap query secara transparan.

[Aplikasi Next.js] ── SELECT * FROM orders; ──▶ [ RLS Engine ] │ (Automated Filter Applied) WHERE outlet_id = 'bogor-id' │ ▼ [ Hasil Terfilter: Hanya order outlet Bogor yang dikembalikan ]

Di Supabase, RLS diaktifkan dengan perintah:

ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- Dan diatur menggunakan POLICY:
CREATE POLICY "Staff can read their own orders" ON orders
  FOR SELECT TO authenticated
  USING (outlet_id = auth.uid()); -- Contoh filter otomatis

⚠️ Bahaya Terbesar: Rekursi RLS (Infinite Loop)

Ini adalah jebakan paling sering bagi developer yang baru belajar Supabase. Misalkan kamu membuat policy untuk tabel outlet_staff seperti ini:

-- ❌ POLICY INI AKAN CRASH (REKURSIF)
CREATE POLICY "Staff can view staff in same outlet" ON outlet_staff
  FOR SELECT TO authenticated
  USING (
    outlet_id = (
      SELECT outlet_id FROM outlet_staff WHERE id = auth.uid()
    )
  );

Kenapa query di atas crash?

  1. Kamu memanggil SELECT * FROM outlet_staff.
  2. RLS terpicu, lalu menjalankan subquery: SELECT outlet_id FROM outlet_staff...
  3. Karena subquery itu membaca tabel outlet_staff, RLS terpicu lagi di dalam subquery.
  4. Subquery baru memicu RLS lagi... terus menerus sampai database crash karena stack overflow.
🌀 Analogi Cermin Berhadapan

Rekursi RLS seperti kamu menaruh cermin di depan cermin lain. Kamu akan melihat bayangan tak terbatas yang masuk ke dalam. Di database, ini akan menghabiskan memori dan mematikan koneksi.

🔑 Senjata Rahasia SS Digital: accessible_outlet_ids()

Untuk menghindari rekursi dan menjaga performa di 19 outlet dengan 11+ role staff yang berbeda, project SS Digital menggunakan fungsi pembantu (Helper Function) bernama accessible_outlet_ids().

Mari kita bedah kodenya dari file migrasi 20260711190000_fix_accessible_outlet_ids_regression.sql:

CREATE OR REPLACE FUNCTION public.accessible_outlet_ids()
RETURNS SETOF uuid
LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public
AS $$
  WITH me AS (
    SELECT id, role, outlet_id FROM public.outlet_staff WHERE id = auth.uid()
  )
  -- 1. Role global (owner, spv, kitchen, dsb) mendapat akses SEMUA outlet
  SELECT o.id FROM public.outlets o, me
    WHERE me.role IN ('admin', 'admin_hr', 'owner', 'spv', 'kitchen', 'admin_finance')
  UNION
  -- 2. Leader / Korlap mendapat akses ke outlet binaannya di tabel pemetaan staff_outlets
  SELECT so.outlet_id FROM public.staff_outlets so, me
    WHERE me.role IN ('leader', 'korlap') AND so.staff_id = me.id
  UNION
  -- 3. Crew / Kiosk mendapat akses hanya ke outlet tempat dia ditugaskan
  SELECT me.outlet_id FROM me
    WHERE me.outlet_id IS NOT NULL
      AND me.role IN ('crew', 'kiosk', 'mitra', 'staff_pusat');
$$;

Mengapa fungsi ini sangat cepat dan aman dari rekursi?

1. Keyword SECURITY DEFINER (Menghindari Rekursi)

Secara default, fungsi berjalan sebagai SECURITY INVOKER (menggunakan hak akses user yang sedang login, sehingga kena aturan RLS). Dengan menyetel SECURITY DEFINER, fungsi ini berjalan menggunakan hak akses pemilik database (admin/postgres). Saat membaca tabel outlet_staff, fungsi ini langsung melewati (bypass) RLS, sehingga **tidak akan pernah terjadi rekursi/infinite loop**.

2. Keyword STABLE (Menghemat CPU)

Dalam PostgreSQL, fungsi STABLE menjamin bahwa jika dipanggil beberapa kali dalam satu query dengan user yang sama, hasilnya pasti sama. Database cukup menjalankan fungsi ini **1 kali saja** di awal query, lalu men-cache hasilnya untuk mencocokkan baris-baris berikutnya. Tanpa STABLE, database harus memanggil fungsi ini berulang-ulang untuk setiap baris yang dibaca (sangat lambat jika tabel berisi ribuan data!).

🚀 Cara Memakai accessible_outlet_ids() di RLS Policy

Dengan adanya helper function di atas, menulis policy RLS untuk tabel-tabel transaksional (seperti ledger_stok, orders, atau attendance) menjadi sangat sederhana dan cepat:

-- Policy RLS SELECT untuk tabel ledger_stok (migration 20260712000000)
CREATE POLICY ledger_read ON ledger_stok
  FOR SELECT TO authenticated
  USING (
    outlet_id IN (accessible_outlet_ids())
  );

Saat crew kasir Bogor melakukan query, database secara otomatis hanya mengevaluasi daftar outlet yang berhak ia akses (yaitu hanya ID outlet Bogor). Sangat ringkas dan aman!
