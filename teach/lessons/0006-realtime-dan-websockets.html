Realtime Subscriptions & WebSockets

Realtime membuat data di layar berubah sendiri tanpa refresh halaman. Mari pelajari cara kerjanya, batasannya, dan apa itu Replica Identity.

🎯 Tujuan Lesson Ini

  • Memahami perbedaan request **HTTP** dengan koneksi **WebSocket**
  • Memahami cara menyaring (filter) realtime agar client tidak menerima sampah data
  • Mengetahui pentingnya REPLICA IDENTITY FULL pada operasi UPDATE & DELETE
  • Menyadari batasan kuota koneksi realtime di Supabase

1. HTTP vs WebSocket: Cara Data Mengalir

Di web biasa (HTTP), client harus bertanya ke server untuk mendapatkan data baru: "Ada order baru?". Server membalas, lalu koneksi ditutup. Jika ingin data baru, browser harus bertanya lagi (Polling).

Di **WebSockets** (Realtime), browser membuka satu gerbang komunikasi permanen. Server dan browser terus terhubung. Begitu ada data masuk ke database, server langsung berteriak mengirimkannya ke browser tanpa ditanya.

HTTP Polling: [Browser] ──── (Tanya data baru?) ───▶ [Server] ── (Balas & Tutup) WebSocket: [Browser] ◀══════ (Gerbang Koneksi Live) ══════▶ [Server] (Siaran Langsung)

2. Menyaring Data Realtime (Filter Client)

Membroadcast data ke semua browser bisa memakan banyak kuota internet dan CPU browser. Di SS Digital, kita selalu menggunakan **filter** di sisi client. Contoh di file useStockAlerts.ts:

-- Hanya dengarkan update tabel stok_balance yang outlet_id-nya sama dengan outlet kasir
supabase
  .channel(`stock_balance_${outletId}`)
  .on(
    'postgres_changes',
    { event: '*', schema: 'public', table: 'stok_balance', filter: `outlet_id=eq.${outletId}` },
    (payload) => {
      -- Jalankan aksi refetch
    }
  )

Bahayanya: Jika filter salah tulis (misal UUID outlet tidak valid atau typo nama tabel), koneksi socket tetap terbuka tetapi **tidak akan ada data yang terkirim**.

3. Apa itu REPLICA IDENTITY FULL?

Secara default, saat baris data di-update atau di-delete, PostgreSQL hanya mengirimkan primary key (misal kolom id) ke log replikasi untuk menghemat memori.

Ini masalah untuk RLS Realtime: Jika browser memfilter outlet_id=eq.Bogor, lalu terjadi operasi DELETE, payload default **tidak membawa kolom `outlet_id` lama**. Akibatnya, filter realtime gagal mengenali bahwa baris yang terhapus itu milik outlet Bogor, dan user tidak mendapat update di layarnya!

Solusinya: Kita menyetel tabel agar mengirimkan seluruh kolom lamanya saat terjadi update/delete:

-- Disetel di file migrasi kita
ALTER TABLE public.ledger_stok REPLICA IDENTITY FULL;

⚠️ Batasan Kuota Realtime Supabase

Supabase memiliki batasan koneksi WebSocket simultan berdasarkan plan project:

  • Free Plan: Maksimal **200 koneksi bersamaan** (200 tab browser terbuka sekaligus).
  • Pro Plan: Maksimal **10.000 koneksi bersamaan**.

Untuk menghemat koneksi, hindari membuka channel socket baru di setiap component React. Kelompokkan subscription dalam satu file hooks global (seperti useMonitoringRealtime di dashboard) agar satu tab browser hanya memakai 1 koneksi socket saja.
