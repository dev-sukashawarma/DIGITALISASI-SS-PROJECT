Mendeteksi & Memperbaiki Query Lambat

Ini skill #1 backend maintenance. Kalau kamu bisa mendeteksi dan memperbaiki query lambat, 80% masalah performa sudah bisa kamu tangani.

🎯 Tujuan Lesson Ini

  • Tahu cara membuka Query Performance di Supabase Dashboard
  • Bisa membaca output EXPLAIN ANALYZE untuk tahu query lambat kenapa
  • Tahu kapan harus tambah index vs rewrite query
  • Bisa menerapkan fix ke project SS Digital yang nyata

🩺 Step 1: Buka "Dokter" Database

Supabase punya fitur bawaan bernama Query Performance — ini seperti laporan kesehatan database kamu. Buka dari dashboard:

📍 Cara Buka Query Performance
  1. Buka supabase.com/dashboard
  2. Pilih project Outlet Suite (bukan Ecosystem)
  3. Klik menu kiri: Database → Query Performance
  4. Lihat tabel: ini daftar query yang paling lambat / paling sering dijalankan
🏥 Analogi Dokter

Query Performance = hasil medical check-up database. Tanpa ini, kamu hanya menebak-nebak. Dengan ini, kamu bisa langsung tahu bagian mana yang "sakit" dan perlu diobati.

ℹ️ Kenapa bisa ada fitur ini?

Project SS Digital sudah mengaktifkan extension pg_stat_statements via migration 20260623120000_enable_pg_stat_statements.sql. Extension ini merekam statistik semua query yang pernah dijalankan di database.

🔬 Step 2: Baca EXPLAIN ANALYZE

Ketika kamu menemukan query yang lambat, kamu bisa "minta penjelasan" ke PostgreSQL dengan perintah EXPLAIN ANALYZE. Ini memberitahu kamu rencana eksekusi query — apa yang terjadi di balik layar.

Contoh Nyata dari Project SS Digital

Misalnya query monitoring stok yang dipanggil saat buka halaman Live Monitoring:

-- Query asli (disederhanakan)
SELECT * FROM monitoring_view_spv
WHERE outlet_id IN (accessible_outlet_ids());

-- Untuk diagnosa, tambah EXPLAIN ANALYZE di depannya:
EXPLAIN ANALYZE
SELECT * FROM monitoring_view_spv
WHERE outlet_id IN (accessible_outlet_ids());

Hasilnya kira-kira seperti ini:

Seq Scan on ledger_stok  (cost=0.00..8234.51 rows=1 width=200)
                         (actual time=42.3..156.7 rows=18 loops=1)
  Filter: (outlet_id = ANY (...))
  Rows Removed by Filter: 89432

Planning Time: 0.8 ms
Execution Time: 157.5 ms   ← ⚠️ Ini lambat!

Cara Baca Output EXPLAIN

Kata KunciArtinyaBaik/Buruk?
Seq Scan Sequential Scan — database baca SEMUA baris satu per satu 🔴 Buruk kalau tabel besar
Index Scan Database pakai index — langsung lompat ke baris yang dibutuhkan 🟢 Bagus
Bitmap Heap Scan Gabungan index + sequential — untuk banyak hasil 🟡 Bisa oke
Rows Removed by Filter Berapa baris yang dibaca tapi dibuang 🔴 Buruk kalau angkanya besar
actual time=X..Y ms Waktu aktual eksekusi 🔴 >100ms perlu perhatian
📚 Analogi Perpustakaan

Seq Scan = petugas cari buku dengan membuka tiap halaman katalog satu per satu dari awal.
Index Scan = petugas langsung buka indeks di belakang buku, lompat ke halaman yang tepat.

Kalau perpustakaan punya 100.000 buku, Seq Scan sangat lambat. Index adalah solusinya.

⚡ Step 3: Kapan Tambah Index?

Index adalah "daftar isi" tambahan di database yang mempercepat pencarian. Tapi tidak semua kolom perlu index — index juga memperlambat operasi INSERT/UPDATE.

Aturan Praktis: Tambah Index Kalau…

✅ Kolom sering dipakai di WHERE, JOIN ON, atau ORDER BY
✅ Tabel punya banyak baris (>10.000 rows) dan query sering Seq Scan
✅ Kolom foreign key yang sering di-JOIN (misalnya outlet_id, bahan_baku_id)
❌ Jangan index kolom yang bisa berubah sangat sering (update ratusan kali/menit)
❌ Jangan index tabel kecil (<1000 rows) — Seq Scan lebih cepat untuk tabel kecil

Index yang Sudah Ada di Project SS Digital

Migration 20260620100000_perf_indexes.sql dan 20260722190000_optimize_pos_indexes_and_queries.sql sudah menambahkan index penting. Contoh:

-- Index pada tabel ledger_stok (tabel paling besar & sering di-query)
CREATE INDEX idx_ledger_stok_outlet_id
  ON ledger_stok (outlet_id);

CREATE INDEX idx_ledger_stok_created_at
  ON ledger_stok (created_at DESC);

-- Index composite (gabungan 2 kolom) — untuk query outlet + waktu sekaligus
CREATE INDEX idx_ledger_outlet_created
  ON ledger_stok (outlet_id, created_at DESC);

🛠️ Step 4: Cara Tambah Index (Praktik)

Kalau kamu menemukan query lambat dan perlu tambah index, buat migration file baru:

-- File: supabase/migrations/20260724100000_fix_slow_query_xxx.sql

-- SELALU pakai CONCURRENTLY agar tidak lock tabel saat index dibuat
-- (penting untuk production yang sedang dipakai!)
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_nama_yang_deskriptif
  ON nama_tabel (nama_kolom);

-- Untuk index composite (urutan kolom penting!):
-- Kolom yang paling selective (nilai paling unik) taruh di depan
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_orders_outlet_status
  ON orders (outlet_id, status, created_at DESC);
⚠️ Penting

Selalu gunakan CONCURRENTLY saat membuat index di database production. Tanpa itu, PostgreSQL akan lock (memblokir) semua operasi tulis ke tabel tersebut sampai index selesai dibuat — bisa beberapa menit untuk tabel besar!

🔍 Step 5: Cara Cepat Cek Semua Index yang Ada

Kamu bisa lihat semua index di database SS Digital dari Supabase SQL Editor:

-- Lihat semua index yang ada
SELECT
  schemaname,
  tablename,
  indexname,
  indexdef
FROM pg_indexes
WHERE schemaname = 'public'
ORDER BY tablename, indexname;

-- Cek index yang TIDAK PERNAH dipakai (kandidat untuk dihapus)
SELECT
  relname AS table_name,
  indexrelname AS index_name,
  idx_scan AS times_used
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY relname;

🏋️ Latihan: Diagnosis Query Views Monitoring

Coba langkah ini di Supabase SQL Editor project SS Digital kamu:

🧪 Praktik Nyata
  1. Buka Supabase Dashboard → SQL Editor
  2. Jalankan query ini: 
    EXPLAIN ANALYZE
SELECT * FROM monitoring_view_spv
LIMIT 20;
  3. Cari baris yang ada kata Seq Scan — itu kandidat masalah
  4. Cari baris Execution Time: — kalau >500ms, perlu dioptimasi
  5. Lihat Rows Removed by Filter — kalau ribuan, butuh index
🧪 Cek Pemahaman

1. Kamu lihat output EXPLAIN: Seq Scan ... Rows Removed by Filter: 95,000. Apa artinya?

2. Kolom outlet_id di tabel ledger_stok (ratusan ribu baris) sering dipakai di WHERE. Apa yang harus dilakukan?

3. Mengapa penting menggunakan CONCURRENTLY saat membuat index di production?
