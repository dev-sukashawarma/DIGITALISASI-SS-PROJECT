Triggers & Cron Jobs: Otomasi & Titik Kegagalan

Otomasi database membuat hidup kita mudah. Tapi jika mereka gagal di latar belakang, efeknya bisa fatal. Mari kita pelajari cara kerjanya di SS Digital.

🎯 Tujuan Lesson Ini

  • Memahami perbedaan peran antara Database Trigger dan Cron Job (pg_cron)
  • Mengetahui arsitektur sinkronisasi data POS menggunakan pg_net
  • Memahami bahaya trigger gagal yang dapat memblokir seluruh aplikasi (Blocking Transaction)
  • Bisa mendeteksi kegagalan cron job menggunakan tabel cron.job_run_details

1. Database Triggers: Pemicu Instan

Trigger adalah aksi otomatis yang dijalankan oleh database *seketika sebelum atau setelah* operasi INSERT, UPDATE, atau DELETE terjadi pada sebuah tabel.

Contoh Nyata: Auto-isi Nomor Order POS Kasir

Dari file migrasi 20260626160000_pos_sales_sync.sql, kita memiliki trigger berikut:

-- 1. Fungsi trigger: jika order_number kosong, isi dari sequence
CREATE OR REPLACE FUNCTION public.fill_order_number()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.order_number IS NULL THEN
    NEW.order_number := nextval('public.pos_sync_order_number_seq');
  END IF;
  RETURN NEW;
END $$;

-- 2. Trigger pemicu: jalan BEFORE INSERT pada tabel orders
CREATE TRIGGER trg_fill_order_number
  BEFORE INSERT ON public.orders
  FOR EACH ROW EXECUTE FUNCTION public.fill_order_number();
🚨 Titik Kegagalan: Blocking Trigger

Trigger BEFORE INSERT bertindak sebagai pintu gerbang. Jika fungsi trigger fill_order_number() mengalami error (misalnya sequence pos_sync_order_number_seq tidak sengaja terhapus), operasi insert akan gagal total. Kasir tidak akan bisa memasukkan pesanan baru sama sekali!

2. Cron Jobs (pg_cron): Penjadwalan Latar Belakang

Berbeda dengan trigger yang bereaksi langsung terhadap perubahan data, Cron Job berjalan berdasarkan **waktu** yang dijadwalkan (misalnya setiap menit, setiap hari jam 12 malam, dsb.).

Supabase menyediakan ekstensi pg_cron untuk menjalankan SQL terjadwal langsung di dalam database.

Contoh Nyata: Pemicu Sinkronisasi POS Sales

Dari file migrasi 20260627100000_schedule_sync_pos_sales.sql, kita menjadwalkan sinkronisasi data POS dari server eksternal setiap 1 menit:

SELECT cron.schedule(
  'sync-pos-sales',   -- Nama job
  '* * * * *',         -- Jadwal (setiap 1 menit)
  $$
    -- Memanggil Edge Function via HTTP POST menggunakan ekstensi pg_net
    SELECT net.http_post(
      url := (SELECT decrypted_secret FROM vault.decrypted_secrets WHERE name = 'project_url')
             || '/functions/v1/sync-pos-sales',
      headers := jsonb_build_object(
        'Authorization', 'Bearer ' || (SELECT decrypted_secret FROM vault.decrypted_secrets WHERE name = 'service_role_key'),
        'Content-Type', 'application/json'
      ),
      body := '{}'::jsonb
    ) AS request_id;
  $$
);
🤝 Kerja Sama pg_cron + pg_net

pg_cron bertindak sebagai alarm jam dinding yang berdering setiap 1 menit.
pg_net bertindak sebagai kurir yang pergi mengirimkan surat (HTTP Request) ke luar database (Edge Function) begitu alarm berdering.

🩺 Cara Diagnosa Kegagalan Cron Job

Karena cron job berjalan di latar belakang, kamu tidak akan melihat error di console browser atau terminal. Jika data POS tiba-tiba berhenti mengalir (dashboard kosong), kamu wajib memeriksa log cron dengan query berikut di SQL Editor:

-- Cek 20 riwayat jalannya cron job terbaru
SELECT
  jobid,
  jobname,
  status,           -- 'succeeded' atau 'failed'
  start_time,
  return_message,   -- Pesan error jika gagal
  database
FROM cron.job_run_details
ORDER BY start_time DESC
LIMIT 20;
⚠️ Penyebab Umum Kegagalan Cron di Supabase
  • HTTP Timeout (504): Edge Function yang dipanggil terlalu lambat merespons (lebih dari 10-30 detik).
  • Secret Kunci Dekripsi Hilang: Kunci project_url atau service_role_key di Vault terhapus atau kedaluwarsa.
  • Beban CPU Tinggi: Database sedang sibuk memproses query lain sehingga pg_cron terlewati (skipped).
