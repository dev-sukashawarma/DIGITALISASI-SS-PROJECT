Migration Hygiene: Menulis SQL Migrasi yang Aman

Project kamu sudah memiliki lebih dari 300 file migrasi database. Mari pelajari cara menulis perubahan database yang aman agar tidak merusak data lama.

🎯 Tujuan Lesson Ini

  • Memahami konsep **Additive Migrations** (Perubahan Aditif)
  • Mengetahui bahaya perintah destruktif seperti DROP COLUMN di database production
  • Bisa menggunakan pertahanan SQL seperti IF NOT EXISTS dan DROP POLICY IF EXISTS
  • Tahu cara menangani konflik riwayat migrasi menggunakan perintah migration repair

1. Aturan Emas: Additive Migrations

Di database production yang sedang aktif melayani transaksi 19 outlet, kamu **tidak boleh** mengubah struktur database dengan cara yang destruktif (merusak).

Gunakan prinsip **Additive Migrations**: buat perubahan database dengan cara menambah (add), bukan menghapus atau mengubah paksa kolom yang sudah ada.

Tindakan Destruktif (Hindari)Tindakan Aditif (Gunakan)
🔴 DROP COLUMN status; (Menghapus kolom lama) 🟢 Biarkan kolom lama, atau buat kolom baru is_active BOOLEAN; lalu salin datanya secara bertahap.
🔴 ALTER COLUMN price SET NOT NULL; (Kolom kosong dipaksa NOT NULL) 🟢 Beri nilai default dulu untuk baris kosong, baru set NOT NULL secara terpisah.
🔴 Mengubah nama tabel langsung 🟢 Buat tabel baru, sinkronkan data secara bertahap, lalu hapus tabel lama setelah aplikasi Next.js diganti kodenya.

2. Menulis SQL dengan Defensif

Karena migrasi bisa dijalankan berulang kali (lokal, staging, produksi), pastikan SQL kamu **idempotent** (bisa dijalankan berkali-kali tanpa menghasilkan error).

Gunakan Pertahanan SQL Ini:

── 1. Untuk Tabel Baru ─────────────────────────────────
CREATE TABLE IF NOT EXISTS public.nama_tabel ( ... );

── 2. Untuk Kolom Baru ─────────────────────────────────
ALTER TABLE public.outlet_staff
  ADD COLUMN IF NOT EXISTS is_active boolean DEFAULT true;

── 3. Untuk Index Baru ─────────────────────────────────
CREATE UNIQUE INDEX IF NOT EXISTS orders_external_order_id_uq
  ON public.orders (external_order_id);

── 4. Untuk RLS Policy Baru (Selalu drop dulu!) ────────
DROP POLICY IF EXISTS "Staff can read categories" ON public.categories;
CREATE POLICY "Staff can read categories" ON public.categories ...;

3. Menangani Riwayat Migrasi Konflik (Diverged History)

Terkadang, database cloud sudah memiliki suatu tabel/fungsi tetapi file migrasi lokal belum tercatat sebagai "sudah dijalankan". Saat kamu menjalankan supabase db push, terminal akan menolak dan memunculkan error konflk.

Solusinya: Gunakan perintah migration repair untuk menandai migrasi tersebut sebagai "sudah diterapkan" di cloud tanpa harus menjalankannya ulang:

# Tandai file migrasi tertentu sebagai "applied" (sudah dijalankan) di remote
supabase migration repair --status applied [timestamp_file_migrasi]

# Contoh:
supabase migration repair --status applied 20260723101000

# Setelah diperbaiki, jalankan push kembali:
supabase db push
🧪 Cek Pemahaman

1. Mengapa perintah DROP COLUMN sangat dihindari di database production yang sedang berjalan?

2. Perintah apa yang digunakan untuk menyelesaikan masalah di mana file migrasi lokal ditolak saat push karena database cloud menganggap riwayat migrasi tidak sinkron?
